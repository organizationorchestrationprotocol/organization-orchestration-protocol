# Maintainer reference mechanisms

The complete current-source derived distribution is generated with `node maintainer/generate-release.mjs`, then accepted locally with `node maintainer/accept-release.mjs`. The generator exports 35 modules and 54 complete source clauses from an explicit semantic allocation; BOOT-01–13 and lifecycle/interface records formalize execution boundaries without replacing semantic judgment. Producer acceptance runs 55 local observations and seven scenarios against the actual package. See `evidence/release-acceptance.json` and `evidence/release-traceability.json` for scope and limitations. These commands never belong in consumer bootstrap and perform no provider effects or runtime installation.

`release-plan.mjs` is a reviewed semantic allocation, not a heading/keyword parser. `release-review.json` binds every approved source span and module dependency to the reviewed source. A source change stops generation until complete semantic review updates that ledger and affected mappings/contracts/tests. Preserve stable clause and observation identities; record actual deltas rather than silently assigning new meanings to old IDs. The current acceptance path covers derived-only regeneration of unchanged canonical semantics: changed source against the latest committed accepted checkpoint requires explicit semantic delta/regression work before acceptance. It must not be labeled an empty-delta generation. On the first complete export the preceding committed source/reference checkpoint is used with its narrower evidence scope disclosed; no prior complete distribution or live result is invented.

The accepted package contains exact semantic source clauses and typed reference boundaries. `$clause` means evaluate that complete clause for the named contract dimension; `$clause+core` also applies Core. It is not a JSON pointer, an automatic boolean conversion or a new authority. Predicates can check necessary attributed facts, but fact authenticity, semantic classification, permissions and installed enforcement remain independently established. Optional native/local implementations may consume these contracts without using the maintainer's Node implementation.

The following tools are historical isolated prototypes, retained as executable reference cases. They do not generate or certify the complete distribution.

These are local producer fixtures, not an installable OOP distribution, consumer prerequisites or proof of live runtime governance. `PROMPT.md` is the only normative source. JSON Schema describes the intended producer contract; the reference engine demonstrates closure, assembly, three-valued guards, selective invalidation, scoped reuse and readiness distinctions. No effects, provider calls, credential enrollment, model calls, installation or repository audit are performed.

Run `node maintainer/export-candidate.mjs`, then `node --test maintainer/reference-engine.test.mjs` for isolated positive/negative/unknown scenarios. Run `node maintainer/benchmark.mjs` for reproducible fixture measurements. These commands belong exclusively to maintenance; do not place them in consumer activation, bootstrap, migration or recovery. Node is a maintainer implementation choice, not a consumer dependency.

`record-evidence.mjs` records the original REL-01–11 change against its original pre-change checkout. It is a retrospective narrow checker, not the new release acceptance command; its original baseline assumptions no longer apply after that source change is committed. Stored historical evidence describes only its recorded subjects.

The fixture catalog and single exported BOOT-11 contract are deliberately incomplete and cannot satisfy REL-02/REL-11. They are not substituted for canonical modules. The restricted schema-profile validator supports only this profile's declared keywords and rejects unsupported features; it is not a general JSON Schema implementation. Its test result applies only to the checked candidate contract. Local test outcomes do not establish complete semantic reading/coverage, installed runtime controls, provider access, cross-runtime compatibility, latest-prior verified regression, publication or consumer adoption. Candidate generation and live adapters require separate complete source-to-derived semantic review and actual integration evidence before distribution readiness.

Historical `fixture-benchmark.json` describes synthetic fixture content only. Current `release-acceptance.json` measures the real selected package context including entry/selector and applicable procedure bytes, local module reads and selection/read/assembly duration; the comparison is full canonical source loading. Token counts, runtime model calls, end-to-end latency and money remain not_measured. Neither result proves product integration or economic savings. `dist/entry.json` is the structured entry after scope-bound producer acceptance; it is not a consumer adoption checkpoint or OOP version manifest.
